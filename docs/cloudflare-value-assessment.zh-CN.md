# Cloudflare 托管 OpenCode 的价值评估

研究日期：2026-11-12。仓库基线：`42b61b2`。

研究方法：检查仓库实现与已安装依赖，核对 OpenCode、Cloudflare 官方资料。
未访问你的云账号、账单或实际运行实例，也没有部署或修改运行配置。
本文区分「代码中已实现」「平台可以提供」「仍需运行验证」，不把三者混为一谈。

## 结论

**对于已经在 Arch Linux 上顺畅使用 OpenCode 的个人开发者，不建议仅为了“云端也能打开”而迁移主力环境。**

这个项目真正可能提供的增量，是一个不依赖本机在线、能独立执行任务的远程 Linux 环境。
它不是更聪明的 OpenCode，也不天然是更快、更便宜、更可靠或更安全的 OpenCode。

建议保留本机作为主力，把云端定位为可选的第二执行位。只有出现反复发生、能明确验收的远程任务，
才继续投入云端基础设施。若未来发展项目，优先考虑「提交任务 → 隔离执行 → 交付 diff/PR/报告」，
而不是复制整套个人工作站。

## 1. 搬上云的究竟是什么

OpenCode 的模型调用与工具执行是两件事。

- 如果本机已经调用远程模型 API，迁移到 Cloudflare 并不会自动换成更强的模型或免除 token 费用。
  网络路径可能改变，但不能据此承诺推理更快。
- 真正迁移的是 shell、项目文件、工具链、插件、会话数据，以及这些进程持有的权限。
- 当前镜像是 Debian 系 Linux，包含 Node.js、Python 和 OpenCode，不是你的 Arch 环境
  （[`Dockerfile`](../Dockerfile)，第 1、9–12、27–49、200–219 行）。
- 当前配置为 OpenCode v2.2.5、单容器、1 vCPU、4 GiB 内存、8192 MB 临时磁盘，容器区域约束为
  `wnam`，Worker placement 为 `aws:us-west-2`
  （[`wrangler.jsonc`](../wrangler.jsonc)，第 18–38 行）。

因此它更像「租了一个远程执行环境」，而不是把本机能力原样升级。

## 2. 三种需求必须拆开判断

| 真实需求                                | 最轻的可行方案                                                      | 是否需要 Cloudflare Containers                            |
| --------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------- |
| 手机、平板或另一台电脑操作本机 OpenCode | OpenCode 自带 Web/配对能力，加适当的 SSH 转发、私有网络或受保护隧道 | 不需要；本机仍须在线                                      |
| 本机关机或休眠后任务继续执行            | 常开家用主机、VPS 或云容器                                          | 需要另一台主机，但不限于 Cloudflare                       |
| 定时、事件驱动、有重试和结果交付的任务  | 常开执行环境，加调度、任务状态、凭据管理与交付机制                  | Cloudflare 可作为实现平台，但仓库目前尚未实现这些任务语义 |

OpenCode v2 官方文档已经提供 Web UI、`opencode pair`、SSH 转发、`pair --remote`，
以及远程运行 `opencode serve` 的方式。[1]
这些是 OpenCode 自身能力，而非本仓库独有。

**隧道解决可达性，不解决本机休眠。** `tmux`、systemd 和远程访问也不会让一台已经断电或休眠的机器继续计算。
如果你的 Arch 主机本来就常开，「独立云主机」带来的新增价值会进一步缩小。

注意：上述配对命令来自当前 v2 文档；仓库也支持 v1，但 v1/v2 命令与认证方式不同，不能混用。

## 3. 对个人开发者，哪些收益真正成立

### 3.1 不依赖本机在线：最有说服力

例如离开电脑后，执行一个边界明确的仓库分析、依赖升级或测试修复任务。
如果任务主要操作已推送的 Git 仓库，不依赖本机数据库、桌面和设备，远程环境比较自然。

但「浏览器关闭后继续运行」「笔记本关机后继续运行」「云容器被回收后可靠恢复」是三个层次。
当前项目不能仅凭用了 Durable Objects，就承诺第三层。

### 3.2 限制误操作对本机的影响：有条件成立

把不熟悉的仓库或高权限实验放进独立容器，可以减少对个人 home 目录的直接影响。
但隔离边界不是“用了容器就安全”：容器里能访问的 Git、模型和对象存储凭据，以及网络服务，
仍然处于 agent 的权限范围内。它不能自动阻止提示注入、恶意依赖、密钥外传或误删远程数据。

本机也能用容器、独立用户或虚拟机建立隔离。因此安全隔离并不是 Cloudflare 的独占优势。

### 3.3 固定环境、统一入口：成立，但收益看使用规模

镜像能固定一组工具版本、减少 Arch 滚动升级对执行环境的影响。
Cloudflare 可以提供 HTTPS 入口，并搭配 Access 做身份控制。
这些对多人使用、频繁重建或后续任务服务更有吸引力；对单人单机则未必抵消维护负担。

当前 `max_instances: 1`、固定单例 ID，共享同一执行环境，**不等于多人/多任务隔离平台**
（[`src/container.ts`](../src/container.ts)，第 109–130 行）。

## 4. 当前实现的关键代价

### 4.1 本机上下文不会自动跟过去

没有自动同步本机未提交文件、未推送分支或本地服务的机制。
你的 Arch 工具链、AUR 包、浏览器登录态、localhost 数据库、Docker 服务、硬件设备、局域网访问和
本地模型都不会天然出现在远程容器中。

可以逐项补齐其中一部分，但每补一项，都在增加第二套开发环境的同步与凭据管理成本。
如果最后需要从云容器连回本机执行核心操作，就要重新问：为什么不直接远程操作本机？

### 4.2 对象存储持久化，不等于本机磁盘体验，也不等于备份

当前 tigrisfs 把 S3 兼容存储挂到 `/root/s3`，workspace 和 XDG 数据目录都位于其中
（[`Dockerfile`](../Dockerfile)，第 80–105、161–183 行）。

- S3 配置不完整时退回临时本地目录；不能指望容器重建后保留这些数据。
- 配置完整但挂载失败时，启动脚本退出，不会静默降级。
- 会话 SQLite、Git 和大量小文件落在对象存储 FUSE 上，需要验证延迟、锁、rename、fsync 与崩溃恢复语义。
  本次没有性能或一致性测试，不能直接断言一定损坏，也不能把“成功挂载”当成可靠性证明。
- 仓库没有应用级备份与恢复流程。OpenCode 自己的 snapshot 也明确不是事务或备份。[2]

Cloudflare 官方说明容器磁盘在重启后重置；持久状态必须另外设计。[4]
官方 FUSE 文档也明确表示，它不提供本地磁盘性能或完整 POSIX 文件系统语义。[7]
平台级可用性、应用状态持久化、应用备份是不同问题。

### 4.3 “10 分钟休眠”存在代码级反证

这是此次研究中最值得先验证的运行假设。

1. `sleepAfter = '10m'`，但 `onStart()` 会通过 `containerFetch()` 打开容器自己的长期 SSE
   （[`src/container.ts`](../src/container.ts)，第 35、50–61、70–106 行）。
2. 当前安装的 `@cloudflare/containers@0.3.7` 在请求开始时增加 `inflightRequests`，
   响应流结束后才减少（`node_modules/@cloudflare/containers/dist/lib/container.js`，第 884–890、955–960 行）。
3. 只要 `inflightRequests > 0`，其 `isActivityExpired()` 就续期并返回 `false`
   （同文件，第 1687–1692 行）。

**推论：只要该内部 SSE 保持连接，容器可能一直不休眠，即使没有用户任务。**
这是静态代码推导，不是已观测的生产事故；需要关闭所有外部客户端，观察容器状态、日志与计费指标来确认。
不能先用「每天只打开两小时」估算账单，再假设其余时间必然不计费。

反过来，SSE watcher 出错后只记录日志、没有重连（[`src/container.ts`](../src/container.ts)，第 97–106 行），也需要验证监测中断后长任务的生命周期。
当前没有任务级 checkpoint、重试或恢复机制。
即使从不触发闲置休眠，宿主机维护等平台事件仍可能停止容器；官方不保证单个实例连续运行固定时长。[6]

### 4.4 “远程沙箱”的凭据边界还不够窄

当前代码把所有字符串型 Worker 环境变量送入容器，配置又使用 `"permission": "allow"`
（[`src/container.ts`](../src/container.ts)，第 21–23、41–46 行；[`config/opencode/opencode.json`](../config/opencode/opencode.json)）。

此外，`SERVER_PASSWORD` 为空会关闭 Worker Basic 门禁；如果另设了容器密码，
Worker 仍会给转发请求注入它，不能把容器内部认证当成外层门禁的替代
（[`src/index.ts`](../src/index.ts)，第 6–12 行；[`src/container.ts`](../src/container.ts)，第 28–31、113–121 行）。
若有外置 Access，实际暴露面取决于其覆盖范围；本次没有检查云端配置，不能断言你的部署已经公开失守。

因此“给不可信任务一个安全环境”可以是目标，但不是当前已经完成的安全保证。
起码需要最小权限凭据、明确的入口认证，以及对不可信代码的边界设计。

### 4.5 成本：等待模型时 CPU 很闲，也仍在付内存和磁盘的钱

官方当前价格为：内存每 GiB-second 0.0000025 美元、CPU 每 vCPU-second 0.000020 美元、
磁盘每 GB-second 0.00000007 美元。内存和磁盘按分配量计费，CPU 按实际使用计费。
Workers Paid 基础费用每月 5 美元，含 Containers 用量 25 GiB-hours、375 vCPU-minutes 和 200 GB-hours。[5]

按当前 4 GiB 内存、8192 MB 磁盘约 8.192 GB、1 vCPU，30 天一个月计算：

| 假设情景                                                       | Containers 资源费/月 | 加上 5 美元基础计划 |
| -------------------------------------------------------------- | -------------------- | ------------------- |
| 全天运行、CPU 接近零：理论费用底线                             | 约 27.13 美元        | 约 32.13 美元       |
| 全天运行、CPU 平均使用 30%                                     | 约 42.23 美元        | 约 47.23 美元       |
| 全天运行、CPU 持续使用 100%                                    | 约 78.52 美元        | 约 83.52 美元       |
| 每天实际运行总计 2 小时、运行时 CPU 平均 30%，其余时间确实停止 | 约 2.85 美元         | 约 7.85 美元        |

这些是情景估算，不是你的实际账单或全包报价。假设账户的上述包含用量都可用于本项目；
不含可能额外产生的 Workers/DO、对象存储及请求、网络、日志费用，也不含模型 token、税费。
如果你已经为其他项目支付基础计划，不应把 5 美元再次算作本项目新增成本；
反过来，若包含用量已被其他项目消耗，也不能再次抵扣。

全天运行的计算示例：内存 `(4 × 720 − 25) × 3600 × 0.0000025 = 25.695` 美元，
磁盘 `(8.192 × 720 − 200) × 3600 × 0.00000007 ≈ 1.436` 美元。
这说明「几乎不占 CPU」不等于「几乎免费」。
磁盘按十进制 MB/GB 估算，依据官方实例限制中的 `2 GB (2000 MB)`；内存 MiB/GiB 使用二进制单位。[8]

最后一行情景必须包括冷启动、无人操作时的等待及休眠宽限期，不能只计打字或模型回答时间。
当前 SSE 常驻疑点没有验证前，不应把它作为默认预算。

## 5. Cloudflare 平台价值与项目价值分开看

Cloudflare 对这种系统的吸引力，是在同一平台组合入口、身份、状态协调、调度、队列和执行环境。
如果你本来就在这个生态构建一个事件驱动的 agent 服务，这种整合有价值。

但现有 Worker 只实现 `fetch`，没有 cron、queue handler、任务记录或 PR 交付流程
（[`src/index.ts`](../src/index.ts)，第 32–42 行；[`wrangler.jsonc`](../wrangler.jsonc)）。
普通 API 调用当然可以由外部脚本触发，但这不等于项目已经实现了任务托管。

还需要分别算三笔账：

- **个人生产力**：是否比现有 Arch 工作流多完成了事情，而非只是多了一个入口？
- **学习收益**：容器生命周期、DO、对象存储与身份集成值得学习，但这是学习价值，不必包装成效率提升。
- **产品价值**：如果别人能提交一个任务并拿到可靠结果，才开始超出「我的远程工作站」的范畴。

若走第三条路线，一个值得验证的设计是：任务输入绑定 Git 提交，临时磁盘承担 checkout、依赖与构建，
对象存储接收必要产物，完成后交付 diff/PR/报告。
这可以避免把整套日常开发文件系统都放在 FUSE 上，但会增加重建、缓存、任务状态和结果交付设计。
它是后续方向，不是建议现在立即重构。

官方另有 `@opencode/sdk/workerd` 的 Durable Object 集成，使用 DO SQLite 和持久事件，
并替换 workerd 中不可用的本地文件系统及进程服务。[3]
它与本项目的 Linux 容器方案不同，不能把那个 SDK 的恢复能力直接算作当前项目的能力。

对于单人常驻工作站，VPS/常开家用主机的普通磁盘、systemd 和 SSH 值得一起比较。
它们不是零维护，公网 VPS 也不天然安全；优势是减少特有的平台适配。
不能脱离地区、规格和现有付费计划，笼统声称哪种一定更便宜。

## 6. 建议的取舍与小实验

### 当前默认选择

1. **主力继续在 Arch Linux。** 不为没有出现的痛点复制整套环境。
2. 若只是想跨设备使用，先验证本机 Web/配对加受保护远程连接是否已经足够。
3. 云端仅接收边界清楚、可从远端 Git 重建、无须个人主目录权限的任务。
4. 先验证休眠账单和数据恢复，再扩大功能；不要一开始就做多租户、全环境同步和复杂调度。

### 用真实任务而非功能清单验证价值

从你实际要做的事情里挑选三个候选任务，例如：

- 离开主机后，对一个已推送仓库完成一次依赖升级，运行检查并生成可审查 diff。
- 夜间对指定提交执行固定检查，交付一份报告。
- 对陌生仓库做可丢弃的分析，不提供个人账号级凭据。

只选择你真的会用的，不为迁就云端而制造需求。后两类的定时触发、结果通知等，当前需要另外实现。

比较四种方式：本机、远程访问本机、常开主机/VPS、当前 Cloudflare 容器。记录：

- 是否真的完成了本机离线时原本做不了的工作？
- 一项任务需要多少次人工干预、同步文件或重新登录？
- 输出是否可审查、可复用，而不只是“会话还活着”？
- 有效执行时间、空闲付费时间与 token 消耗分别是多少？
- 重启后能恢复哪些数据？未完成任务怎么处理？
- 这是否成为反复使用的工作流，而非新鲜感驱动的演示？

如果没有反复发生的增量收益，保留它为学习项目或按需实验即可。
如果收益成立，则把项目收敛到「可靠交付一个任务」，再决定是否扩大。
